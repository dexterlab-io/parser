# DexterLab Versioning and Compatibility Guide

(Version 2026 — Release Management, Compatibility, and Evolution Policy)

This document defines the versioning policy, compatibility guarantees, deprecation rules, and long-term evolution strategy of the DexterLab ecosystem.

Its purpose is to ensure that:

- Command files remain stable.
- Integrations remain predictable.
- Documentation remains synchronized.
- Future features can be introduced without breaking existing systems.

---

# 1. Versioning Philosophy

DexterLab follows a stability-first approach.

The command language is considered the most important external interface of the framework.

Whenever possible:

```text
Old command files should continue to work.
```

The parser, arbiter, and backend layers may evolve internally without affecting user-visible command behavior.

---

# 2. Version Numbering

DexterLab uses:

```text
MAJOR.MINOR.PATCH
```

format.

Example:

```text
1.1.0
```

---

## MAJOR Version

Incremented when:

- Backward compatibility is broken
- Command syntax changes
- Core interfaces change
- Architecture changes require user action

Example:

```text
1.x.x → 2.x.x
```

---

## MINOR Version

Incremented when:

- New commands are added
- New backends are introduced
- New parser capabilities appear
- Functionality is expanded

without breaking existing workflows.

Example:

```text
1.1.x → 1.2.x
```

---

## PATCH Version

Incremented when:

- Bugs are fixed
- Documentation is corrected
- Internal improvements are made
- No user-visible behavior changes

Example:

```text
1.1.0 → 1.1.1
```

# 4. Compatibility Guarantees

DexterLab attempts to preserve compatibility in four areas:

---

## Command File Compatibility

Files written for a previous release should continue to execute whenever possible.

Example:

```text
WRITE 0x1000 0x12345678
```

must remain valid across compatible releases.

---

## Interface Compatibility

Primary interfaces:

```text
t_cmd_out
t_rsp_out
t_rsp_in
```

should evolve conservatively.

Field additions are preferred over incompatible modifications.

---

## Backend Compatibility

Adding a backend must not change command semantics.

Example:

```text
READ
WRITE
CHECK
```

should behave identically across:

```text
Generic
AXI-FULL
AXI-LITE
AHB-FULL
AHB-LITE
```

---

## Documentation Compatibility

Documentation should remain synchronized with implementation.

Deprecated concepts must be explicitly identified.

---

# 5. Deprecation Policy

Features should not be removed immediately.

Preferred lifecycle:

```text
Active
   |
Deprecated
   |
Legacy
   |
Removed
```

---

## Active

Fully supported.

Used throughout the documentation.

---

## Deprecated

Still supported.

Replacement exists.

New projects should avoid adoption.

---

## Legacy

Retained only for compatibility.

May disappear in future releases.

---

## Removed

No longer supported.

May remain documented only as historical information.

---

Status:


```text
Dedicated backends provide protocol execution directly.
```

---

## Atomic Mode Evolution

```text
cmd_atomic
```

Current architecture uses:

```text
cmd_lock
```

generated by:

```text
SET_ATOMIC
```

Status:

```text
Deprecated terminology removed.
```

# 7. Command Language Evolution

New commands may be added through MINOR releases.

Example:

```text
Future command
```

```text
TRACE_READ
```

could be introduced without affecting existing files.

Rules:

- Existing syntax remains valid.
- Existing commands preserve semantics.
- Command behavior remains deterministic.

---

# 8. Backend Evolution

Future backends may include:

```text
APB
Wishbone
CHI
Custom Protocols
```

Provided they support:

```text
t_cmd_out
t_rsp_out
t_rsp_in
```

they can integrate into the existing architecture.

---

# 9. Future Hardware Master Evolution

Future command sources may include:

```text
RISC-V
DMA
Accelerators
Remote Systems
```

Compatibility requirement:

```text
Generate standard t_cmd_out
Consume standard t_rsp_in
```

This preserves interoperability with existing infrastructure.

# 11. Long-Term Stability Goals

DexterLab aims to provide:

- Stable command language
- Stable interfaces
- Stable arbitration model
- Stable error model
- Predictable upgrades

while allowing:

- New protocols
- New masters
- New debugging capabilities
- New verification features

---

# 12. Summary

DexterLab follows a conservative compatibility strategy.

Core principles:

```text
Command files remain stable.

Interfaces evolve carefully.

Deprecated features are identified explicitly.

Architecture changes are documented.

Backward compatibility is preferred whenever practical.
```

These rules allow the framework to evolve while protecting users, integrations, and existing verification environments.
